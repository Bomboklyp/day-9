# Компромиссы

| Решение | Почему выбрано | Ограничение / когда менять |
| --- | --- | --- |
| Nuxt + Nitro одним приложением | Один проект и один origin для UI, API и cookies | Отдельный backend понадобится при независимом масштабировании |
| PostgreSQL и SQL через pg | Явные запросы и транзакции, без второго слоя генерации моделей | Типы ответа и SQL нужно согласовывать тестами |
| Сессия в БД, HttpOnly cookie | Logout действительно отзывает сессию на сервере | Нужны периодическая очистка истёкших сессий и HTTPS на хостинге |
| Pinia только для UI | Заявки не дублируются в глобальном store | Обновление useAsyncData после мутации нужно выполнять явно |
| Optimistic только для приоритета | Быстрое простое действие; при 409/500 выполняется rollback | Смена статуса требует серверных правил и подтверждения |
| Вложения в bytea | Файл, метаданные и счётчик сохраняются атомарно, без отдельного сервиса | 5 файлов по 10 МиБ; для большого объёма нужен object storage и антивирусная проверка |
| SLA в календарных минутах | Детерминированные правила и понятные тесты | Нет рабочего календаря, часовых поясов организации и паузы на ожидании |
| Таймер SLA в Nitro | Не нужен отдельный worker для учебного развёртывания | Сервер должен постоянно работать; уникальные ключи защищают от дублей при нескольких экземплярах |
| SSR + prerender публичных страниц | Содержимое есть в первом HTML; кабинет не попадает в статическую сборку | При смене домена нужны пересборка sitemap и prerender metadata |
| Миграции отдельным Compose-сервисом | Приложение ждёт успешной подготовки БД | Migration image содержит инструменты разработки; runtime image содержит только .output |
| Ограничение входа в PostgreSQL | Счётчик не исчезает после рестарта и обновляется атомарно | Лимит по паре адрес/почта, без защиты от распределённой атаки; за reverse proxy все запросы могут иметь один адрес |
| Базовая CSP | Закрывает встраивание, object и подмену base без нарушения Nuxt | Это не строгая script-src policy; nonce-based CSP потребует отдельной проверки SSR и inline scripts |
| Публичные учебные аккаунты | Проверяющий может войти в любую роль | Это демонстрационный стенд с открытым паролем, его нельзя наполнять реальными данными |

Границы и три ADR-lite описаны в [ARCHITECTURE.md](ARCHITECTURE.md) и `docs/adr`. Продакшен для реальных клиентов дополнительно требует резервного копирования с проверкой восстановления, мониторинга, управления секретами и закрытия учебных аккаунтов. Эти функции не добавлялись в учебный интерфейс.
