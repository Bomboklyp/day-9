# Изменения продукта — День 8

## SLA

| Приоритет API     | В интерфейсе | Реакция  | Решение |
| ----------------- | ------------ | -------- | ------- |
| urgent / Critical | Критический  | 15 минут | 1 час   |
| high / High       | Высокий      | 1 час    | 4 часа  |
| medium / Normal   | Обычный      | 4 часа   | 24 часа |
| low / Low         | Низкий       | 8 часов  | 72 часа |

Это начальные значения Figma. Admin меняет каждую пару через `/admin/sla`. Сервер принимает целые минуты от 1 до 43 200; решение не может быть раньше реакции. Значения сохраняются в `sla_policies`.

Заявка хранит конкретные `response_due_at` и `due_at`. Новая политика применяется при создании и при смене приоритета; сроки вычисляются от `created_at`. Уже установленные сроки остальных заявок не пересчитываются. Такой снимок позволяет объяснить, какие обязательства действовали для конкретной заявки.

Реакция фиксируется первым назначением/началом обработки или комментарием сотрудника. Решение фиксируется переходом в `resolved`, закрытие — в `closed`. При возврате из решения в работу отметка решения очищается. Срок при этом не начинается заново.

Время календарное, без рабочих графиков; ожидание и эскалация не приостанавливают SLA. Требования не задают календарь и правила паузы. Приближение — последние 20% интервала, но не больше 30 минут и не меньше минуты. Окно не превышает общую длительность SLA. Минимальное окно позволяет таймеру не пропустить предупреждение при коротких пользовательских настройках. После завершения фазы её соблюдение сравнивается с моментом завершения, а не с текущим временем.

## Эскалация

Статус `escalated` добавлен в типы, общий граф переходов, фильтры, SQL constraint и аналитику. Operator/Admin может эскалировать из `assigned`, `in_progress`, `waiting`; нужны причина и доступ к заявке. Назначенный Agent может продолжить работу или зафиксировать решение.

Причина обязательна и при повторном запросе с уже установленным статусом `escalated`. Пустую причину отклоняет API с 422; дополнительно действует constraint БД. История и уведомление сохраняются в той же транзакции, что и статус.

## Вложения

Лимиты по макету: PNG, JPG/JPEG, PDF; максимум пять файлов; каждый до 10 × 1024 × 1024 байт. Клиент и сервер используют общие численные ограничения. Сервер проверяет байты, сигнатуру формата, расширение, имя и текущий счётчик вложений.

Общий multipart body ограничен 51 МиБ при чтении потока, до разбора FormData. При превышении размера возвращается 413, при неверном содержимом — 415, при нарушении количества — 422. Сервис блокирует родительскую заявку, поэтому две параллельные загрузки по три файла не превращаются в шесть сохранённых файлов.

Байты и метаданные хранятся в PostgreSQL. Для небольшого учебного проекта это упрощает транзакции, восстановление и очистку тестовой базы. Цена — увеличение размера БД и чтение ограниченного upload в память. Для большого объёма файлов следующим самостоятельным изменением может стать объектное хранилище; сейчас оно не требуется.

Скачивание проверяет текущий доступ к заявке. Ответ имеет Content-Disposition attachment и X-Content-Type-Options nosniff. Файл не лежит по публичному URL. В закрытую заявку добавить файл нельзя.

## Уведомления

Уведомление имеет получателя, заявку, тип, текст, дату и `read_at`. О назначении, эскалации и статусе сообщения создаются внутри транзакции изменения заявки. Получатели: автор, текущий исполнитель и активные Operator/Admin. Неактивные пользователи исключаются.

Проверка SLA работает серверным таймером раз в 30 секунд; при чтении списка также запускается проверка. Заголовок приложения обновляет список раз в 30 секунд. Работает только при запущенном Node-сервере; отдельный внешний сервис не требуется.

Ключ `user_id + dedupe_key` уникален. Для изменения заявки ключ содержит revision, для предупреждения SLA — фазу и конкретный deadline. Повторная проверка не создаёт копии. Read API помечает записи только текущего пользователя; нельзя пометить чужое уведомление как прочитанное.

Чтение повторно сверяет доступ к заявке: бывший исполнитель после переназначения не получает данные через старую запись. Показываются последние 100 доступных уведомлений. Это внутренние уведомления WorkFlow, без email и сторонних отправок.

## Аналитика

Admin видит все заявки за выбранный период, включая закрытые. Период задаётся query-параметром `period=all|1|7|30`; числа означают последние 24 часа, семь или тридцать суток.

- Всего — количество заявок выбранного периода.
- Закрыто — количество со статусом `closed`.
- SLA соблюдён — доля завершённых заявок, у которых и реакция, и решение уложились в соответствующие сроки. При отсутствии завершённых заявок показывается «—».
- Среднее решение — время от создания до решения/закрытия только завершённых заявок.
- Статусы включают `escalated`.
- Загрузка — незавершённые заявки у каждого Agent. Неактивный сотрудник с оставшимися назначениями тоже виден администратору.

Числа вычисляются SQL-запросами, не копируются из Figma.

## Схема и воспроизводимость

`database/schema.sql` — исходная совместимая схема предыдущего дня. `database/migrations/001-product.sql` добавляет поля SLA и эскалации, таблицы политик, файлов, уведомлений и новые constraints.

`tools/migrate-db.ts` последовательно применяет SQL-файлы и записывает версии в `schema_migrations`. Миграции выполняются в транзакции с advisory lock. Повторный запуск пропускает уже применённую версию. Выполненный SQL-файл не следует редактировать для следующего обновления — нужно добавить новый.

```sh
npm run db:init
```

Команда применяет базовую схему, миграцию и seed. Для существующих заявок один раз заполняется срок реакции и исторические отметки, прежний срок решения сохраняется. Seed не перезаписывает пользовательские заявки и изменённые политики.

Автоматическая проверка создаёт отдельную схему старого формата с сохранённой заявкой, обновляет её, повторяет миграцию и проверяет сохранность записи. Затем отдельно проверяется чистая установка. После тестов обе временные схемы удаляются.

## Тесты

`tests/unit/product.test.ts` проверяет сроки, перевод текста в минуты, эскалацию, границы предупреждения и завершения SLA, лимиты и сигнатуры файлов.

`tests/integration/product-http.ts` использует реальный PostgreSQL и HTTP: роли, настройка SLA, deadlines, эскалация, видимость уведомлений, прочтение, дедупликация, параллельный лимит вложений, реальные скачанные байты и изменения аналитики.

`tests/e2e/product.spec.ts` проверяет состояния из Figma, повтор после 500, сохранение после refresh, эскалацию, загрузку и скачивание, три ширины и доступ по роли. Все прежние сценарии также входят в полный прогон.
