# SSR, hydration и производительность — День 6

> Сохранённый отчёт предыдущего этапа. Его измерения относятся к версии шестого дня; это не финальные замеры. Текущий аудит: [PERFORMANCE.md](../PERFORMANCE.md).

## Условия измерений

Сравниваются одни и те же три страницы шестого дня: главная `/`, центр помощи `/help`, статья `/articles/kak-sozdat-zayavku`. Версия «до» уже содержит новые публичные страницы и metadata. Это сравнение оптимизаций, а не сравнение пустого приложения с готовым.

Production-сборка Nuxt 4.6.4, Nitro, Node.js 24.22.3, Windows, headless Chrome 157.0.0.0, Lighthouse 13.6.0. По три последовательных холодных запуска каждой страницы: 18 аудитов всего. Профиль: mobile 360×800, DPR 1, simulated throttling, CPU ×4, RTT 150 мс, пропускная способность 1638,4 Кбит/с. Сборка и тесты во время замеров не запускались. Сервер локальный, поэтому реальную задержку удалённого хостинга здесь не измеряем.

До: 23.11.2026 21:31 UTC; после: 23.11.2026 21:47 UTC. В таблицах приведены медианы трёх запусков для каждой метрики, а не один выбранный лучший результат. Каждый JSON содержит время, параметры, все отдельные измерения и hash выбранных исходных файлов.

Данные: [before.json](performance/before.json), [after.json](performance/after.json). Полные исходные отчёты всех 18 аудитов: [lighthouse-reports.zip](performance/lighthouse-reports.zip).

У главной медианный LCP уменьшился примерно на 37%, передача JavaScript — на 65%. Большая часть уменьшения байтов связана со сжатием файлов. Объём декодированного JS снизился только примерно на 4–5%: Nuxt и Vue всё ещё нужны для меню, поиска и остальных интерактивных действий. Отложенные виджеты загружаются позже, а не исчезают из приложения.

Это пакет изменений, поэтому таблица не доказывает отдельный вклад каждой оптимизации. Lighthouse CPU benchmark различался: 1103–1498,5 до, 1805,5–2340,5 после. Состояние Windows и фоновые процессы влияют на CPU-метрики; всё снижение TBT нельзя приписать только коду. Размеры ресурсов, HTTP-ответы и исправление hydration проверены отдельно. Для точного сравнения CPU потребовались бы дополнительные чередующиеся прогоны на изолированной машине. Здесь фиксируем учебный baseline, медианы и это ограничение.

## Выбор рендеринга и доступа

| Маршрут                                             | Режим                                                        | Причина                                                                      |
| --------------------------------------------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| `/`                                                 | Предрендеринг                                                | Одинаковый лендинг для всех, HTML создаётся при сборке                       |
| `/articles/:slug` для четырёх опубликованных статей | Предрендеринг                                                | Статические инструкции, доступные без входа                                  |
| `/faq`, `/help`, `/articles`                        | SSR                                                          | Содержательный первый HTML с учётом поиска и категории                       |
| `/login`, `/register`                               | SSR, noindex, private/no-store                               | Формы входа не нужны в поиске                                                |
| `/dashboard`, `/requests/**`, `/profile`            | SSR с сессией, без предрендеринга, private/no-store, noindex | Данные зависят от пользователя и не должны попадать в общий статический HTML |
| Несуществующая статья или сущность                  | HTTP 404                                                     | Статус отсутствующей сущности, а не страница ошибки с HTTP 200               |

Публичный API разрешает без сессии только GET каталога и отдельной статьи. Остальные API защищены как в четвёртом и пятом дне. `robots.txt` и `noindex` не заменяют проверку прав.

Metadata создаёт `app/composables/usePageSeo.ts`: уникальные title, description, canonical, Open Graph и Twitter card. Общий OG-рисунок имеет размер 1200×630. Sitemap содержит восемь открытых URL. Варианты поиска получают canonical основной страницы и `noindex,follow`. Для FAQ JSON-LD содержит только видимые вопросы.

Перед реальной публикацией необходимо задать `NUXT_PUBLIC_SITE_URL` и пересобрать проект: canonical, OG и sitemap предрендеренных страниц фиксируются при сборке. Сейчас они указывают на локальный адрес 127.0.0.1:3005. Внешний домен не настраивался.

## Воспроизведённый hydration mismatch

Отдельного примера от Октагона нет, поэтому проверено текущее приложение. При переходе на предрендеринг обнаружен реальный случай:

1. Открыть статью, оценить её «Да», сохранить cookie `workflow-article-vote-kak-sozdat-zayavku=yes`.
2. Обновить страницу. Предрендеренный HTML создан без личной cookie.
3. Раннее чтение `useCookie` добавляло в первую клиентскую разметку сообщение «Спасибо за ответ», которого нет в серверной разметке.
4. Vue выводил `Hydration node mismatch` и `Hydration completed but contains mismatches`.

Исправление в `ArticleFeedback.vue`: начальная оценка `null` одинакова на обеих сторонах; сохранённое значение применяется в `onMounted`, затем обычный Vue-рендер показывает результат. Текст статьи не обёрнут в ClientOnly. Дата публикации разбирается без локального часового пояса, поэтому не превращается в предыдущий день.

Зафиксированы реальные сообщения [до](performance/hydration-before.json) и пустой список предупреждений [после](performance/hydration-after.json). Проверка:

```sh
npm run build
npx tsx tools/check-hydration.ts
```

Скрипт запускает production-сервер на 3306, новый headless Chrome с сохранённой cookie, прокручивает к отложенному виджету и проверяет сообщение. E2E дополнительно проверяет America/Los_Angeles и Asia/Tokyo, refresh, изменение оценки, сохранённые настройки и отсутствие ошибок консоли. Все проверки прошли.

Флаг `--expect-mismatch` применялся только для фиксации дефекта до исправления; на исправленной версии ожидаемый mismatch отсутствует.

## Как повторить измерения

```sh
npm ci
# Создать .env по .env.example; для публичных страниц SQL-запросы не нужны.
npm run build
npm run perf -- after
```

Нужен Chrome; нестандартный путь задаётся `CHROME_EXECUTABLE`. Скрипт запускает свой собранный сервер на 3206 и закрывает созданные им процессы. Пользовательский браузер и его профиль не используются. Полные отчёты записываются в `.verification/day6/lighthouse/after`, сводка — в `docs/performance/after.json`.

Для повтора исторического baseline нужна отдельная версия шестого этапа. В финальном репозитории сохранены исходные измерения до и после, а текущая версия измеряется командой `npm run perf -- release`.
